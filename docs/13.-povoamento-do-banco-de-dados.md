# 13. Povoamento do Banco de Dados

#### 13.1. Objetivo

Após a implementação da estrutura física, foi realizado o povoamento do banco de dados com informações fictícias.

O objetivo foi simular situações reais de utilização do BarberFlow, permitindo validar os relacionamentos entre as tabelas e preparar o ambiente para a execução de consultas SQL.

#### 13.2. Distribuição dos registros

A demonstração foi ampliada para 600 registros de negócio, com o triplo da quantidade original em cada uma das oito entidades:

| Tabela | Registros |
| --- | ---: |
| Barbearias | 15 |
| Clientes | 105 |
| Cliente\_Barbearia | 150 |
| Barbeiros | 45 |
| Serviços | 75 |
| Planos | 30 |
| Agendamentos | 120 |
| Assinaturas | 60 |
| **Total** | **600** |

Usuários, permissões e expedientes são tabelas técnicas de suporte e não compõem esse total. Há uma conta Barbearia separada para cada uma das 15 unidades no perfil de demonstração.

#### 13.3. Execução e validação

A inserção dos dados foi realizada por meio de um script SQL específico, respeitando a dependência entre as tabelas e seus relacionamentos.

Após a execução, foram realizadas consultas `SELECT` para verificar a presença dos registros e confirmar que a população inicial ocorreu corretamente.

#### 13.5. Ampliação versionada da demonstração

O anexo de 200 registros documenta a população original e é preservado como referência. A ampliação é aplicada por `backend/src/main/resources/db/demo/V5__triplicar_demonstracao.sql`, após a migração original, exclusivamente no perfil de demonstração. O Flyway executa cada migração uma única vez; reinicializações não duplicam os registros. São preservadas as chaves estrangeiras e ajustadas as sequências de todas as entidades. As cópias têm nomes e e-mails fictícios distintos, preços variados, períodos históricos e reservas futuras.

A validação automatizada verifica a quantidade de cada tabela, os 600 registros de negócio, agendamentos distribuídos nas 15 unidades, a ausência de uma segunda execução e o próximo ID disponível.
